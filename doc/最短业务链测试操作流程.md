# 最短业务链测试操作流程

本文用于团队在 Sepolia 上完整测试一次“角色授权 → 发票确认 → 融资报价 → 放款 → 还款分账”。实际产品界面使用英文，本文按界面上的英文名称说明操作。

## 1. 测试账户与参数

准备四个 MetaMask 账户，避免业务参与方地址冲突：

| 账户 | 用途 | 建议 Sepolia ETH |
|---|---|---:|
| Account A | Admin，部署 RoleRegistry 的账户 | 0.05 ETH 以上 |
| Account B | Supplier | 0.02 ETH 以上，用于 Gas |
| Account C | Buyer | 0.07 ETH 以上，用于还款和 Gas |
| Account D | Funder | 0.06 ETH 以上，用于放款和 Gas |

建议使用以下业务数据：

| 字段 | 测试值 |
|---|---|
| Invoice number | `INV-TEST-001` |
| Face value | `0.05 ETH` |
| Principal | `0.04 ETH` |
| Maximum rate | `800 bps`，即 8% |
| Offer rate | `600 bps`，即 6% |
| Holdback | `1000 bps`，即 10% |
| Financing deadline | 当前时间之后 1 天，并早于发票到期日 |
| Invoice due date | 当前日期之后至少 7 天 |

所有账户都必须切换到 Sepolia。测试 ETH 同时用于业务资金和 Gas，不需要 MockUSD。

## 2. 部署后配置

1. 按 `contracts/README.md` 中的顺序部署四份合约。
2. 使用 Account A 调用 `InvoiceRegistry.configureOperators(financingMarket, financingPool)`。
3. 使用 Account A 调用 `FinancingMarket.configurePool(financingPool)`。
4. 把四个合约地址填入 `frontend/.env` 和 `backend/.env`。
5. 在 `backend/.env` 填写可用的 `SEPOLIA_RPC_URL`。
6. 重启前端和后端。
7. 打开应用，确认 Profile 页面显示钱包已连接、网络为 Sepolia，并且平台服务处于可用状态。

## 3. 申请并批准角色

### 3.1 Supplier 申请

1. MetaMask 切换至 Account B。
2. 在应用中连接钱包并完成 `Sign in`。
3. 顶部角色选择 `Supplier`。
4. 进入 `Activity → Roles`。
5. 在 `Supplier` 角色卡片点击 `Request role` 并确认交易；卡片应从 `Not active` 变为 `Pending`。

### 3.2 Buyer 申请

1. MetaMask 切换至 Account C，并重新连接及签名登录。
2. 顶部角色选择 `Buyer`。
3. 进入 `Activity → Roles`，在 `Buyer` 卡片申请角色。

### 3.3 Funder 申请

1. MetaMask 切换至 Account D，并重新连接及签名登录。
2. 顶部角色选择 `Funder`。
3. 进入 `Activity → Roles`，在 `Funder` 卡片申请角色。

### 3.4 Admin 批准

1. MetaMask 切换至 Account A。
2. 顶部角色选择 `Admin`，进入 `Activity → Roles`。
3. 在 `Pending requests` 列表中找到 Account B、C、D 的申请卡片，分别点击 `Approve`。钱包地址和角色由应用自动带入。
4. 在 `Transactions` 中确认三笔交易均为 `confirmed`。

顶部角色选择器会显示每个角色的 `Active`、`Pending` 或 `Not active` 状态。切换角色会改变当前工作视图，操作权限以 RoleRegistry 的链上状态为准。

## 4. Supplier 创建发票

1. 切换至 Account B，选择 `Supplier` 视图并完成签名登录。
2. 进入 `Activity → Invoices`。
3. 在 `Create invoice` 中填写：
   - Buyer wallet：Account C 地址；
   - Invoice number：`INV-TEST-001`；
   - Face value：`0.05`；
   - Issue date：当天；
   - Due date：至少 7 天后；
   - Document hash：可以留空，应用会根据发票号生成测试哈希。
4. 点击 `Submit invoice` 并确认交易。
5. 页面顶部出现成功提示后，发票会自动出现在 `Your invoices` 列表，无需从 Etherscan 查询 ID。

预期结果：发票状态为 `PendingConfirmation`，Home 的 Invoices 区域出现该发票记录。

## 5. Buyer 确认发票

1. 切换至 Account C，选择 `Buyer` 视图。
2. 进入 `Activity → Invoices`。
3. 在 `Invoices for your review` 找到 `0.05 ETH` 的待确认发票。
4. 直接点击该发票卡片上的 `Confirm` 并确认交易。

预期结果：链上发票状态变为 `Confirmed`。如果点击 `Reject`，发票将进入终态 `Rejected`，不能继续本次融资测试。

## 6. Supplier 发起融资

1. 切换至 Account B，选择 `Supplier` 视图。
2. 进入 `Activity → Financing`。
3. 在 `Ready for financing` 找到刚确认的 `0.05 ETH` 发票，在卡片中填写：
   - Funding amount：`0.04`；
   - Maximum rate：`800`；
   - Holdback：`1000`；
   - Offer deadline：当前时间后 1 天，并确保早于发票到期时间。
4. 点击 `Request financing` 并确认交易。页面会自动刷新该申请的链上状态。

预期结果：融资状态为 `Open`，发票状态为 `FinancingOpen`。

## 7. Funder 报价

1. 切换至 Account D，选择 `Funder` 视图。
2. 进入 `Activity → Financing`。
3. 在 `Open opportunities` 找到金额为 `0.04 ETH` 的申请，在卡片中输入 Annual rate `600`。
4. 点击 `Submit offer` 并确认交易。

预期结果：报价为 `Active`，利率低于融资申请允许的 `800 bps`。

## 8. Supplier 接受报价

1. 切换至 Account B。
2. 进入 `Activity → Financing`，在 `Your financing requests` 找到 6% APR 的报价。
3. 直接点击该报价右侧的 `Accept` 并确认交易。

预期结果：融资状态为 `OfferAccepted`；Account D 获得 24 小时放款窗口。

## 9. Funder 放款

1. 切换至 Account D。
2. 在 `Ready to fund` 找到已接受的 `0.04 ETH` 申请。
3. 点击 `Fund 0.04 ETH`。应用会自动带入融资 ID 和精确金额，在 MetaMask 中核对后确认。

预期资金变化：

- Funder 支付 `0.04 ETH`，另付 Gas；
- Holdback 为 `0.004 ETH`；
- Supplier 首笔收到 `0.036 ETH`；
- 融资状态变为 `Funded`；
- 发票状态变为 `Funded`。
- Funder 的项目保留在 `Your offers and investments`，显示 `Funding sent · Awaiting buyer repayment`。

发送金额少于或多于 `0.04 ETH` 都应回滚。

## 10. Buyer 还款并自动分账

1. 切换至 Account C。
2. 在 `Repayments due` 找到 `0.05 ETH` 的已放款发票。
3. 点击 `Repay 0.05 ETH`。应用会自动带入发票 ID 和精确面值，确认 MetaMask 交易。

预期结果：

- Buyer 支付 `0.05 ETH`，另付 Gas；
- Funder 收到 `principal + interest`；
- Treasury 收到平台费；
- Supplier 收到剩余票款及释放的 Holdback；
- 发票状态变为 `Repaid`；
- 融资状态变为 `Settled`；
- 合约不应遗留本次业务中可分配的资金。
- Buyer 可在 `Payment history` 查看已还款记录，Funder 的项目显示 `Investment repaid and settled`。

实际利息根据放款时间到发票到期日的向上取整天数计算，因此应以 `FinancingFunded` 事件和链上余额变化为准。

## 11. 建议补测的失败场景

| 场景 | 预期结果 |
|---|---|
| 未批准角色的钱包提交发票或报价 | 交易回滚 |
| Supplier 与 Buyer 使用同一地址 | 发票提交回滚 |
| 非指定 Buyer 确认发票 | 交易回滚 |
| 报价利率高于最高利率 | 报价回滚 |
| Supplier 接受属于其他融资的 offerId | 交易回滚 |
| 非选中的 Funder 放款 | 交易回滚 |
| 放款 ETH 不等于 Principal | 交易回滚 |
| 非指定 Buyer 还款 | 交易回滚 |
| 还款 ETH 不等于 Face value | 交易回滚 |
| 对已还款发票再次还款 | 交易回滚 |

每次失败后，当前页面顶部应立即显示可读错误；`Transactions` 会保留完整状态和 Etherscan 链接。等待现有交易结束后再重试，避免重复发送资金交易。
