# SME Flow 应收账款融资平台用户操作手册

## 1. 手册说明

SME Flow 是一个运行在 Ethereum Sepolia 测试网上的应收账款融资平台。供应商可以登记经买方确认的应收账款并申请提前融资，资金方可以提交融资报价和放款，买方负责确认发票并偿还票面金额，仲裁员负责处理争议，审计员可以查看链上状态、资金流和事件记录。

本手册面向平台的实际使用者，说明如何连接钱包、取得角色权限并完成各角色对应的业务操作。界面中的按钮和状态名称使用英文，本手册在说明时保留对应的英文名称，便于对照操作。

当前平台使用 Sepolia 测试 ETH。测试 ETH 不具有真实货币价值，请勿向平台合约发送主网 ETH 或其他真实资产。

### 1.1 业务流程概览

一笔应收账款融资通常按照以下顺序进行：

1. 参与者连接钱包并取得所需角色权限。
2. Supplier 创建发票，并指定负责确认和付款的 Buyer。
3. Buyer 核对发票信息，选择确认或拒绝。
4. 发票确认后，Supplier 设置融资本金、最高利率、Holdback 和报价期限。
5. Funder 提交利率报价，Supplier 从有效报价中选择一个接受。
6. 被选中的 Funder 支付融资本金，Supplier 立即收到扣除 Holdback 后的款项。
7. Buyer 支付完整发票票面金额，合约自动向 Funder、Supplier 和 Treasury 分账。
8. Auditor 可以通过只读页面核对最终状态、资金流和链上事件。

如果业务发生异常，还可能进入以下分支：

- 发票到期后仍未还款，可以被标记为 `Overdue`；超过 3 天宽限期后，可以被确认为 `Defaulted`。
- Supplier、Buyer 或参与融资的 Funder 可以发起争议。争议期间融资操作被冻结，但 Buyer 仍可以还款，资金会暂存在合约中，等待 Arbitrator 裁决。

每一步可执行的操作由当前钱包、角色、业务状态和时间条件共同决定。用户不需要手动修改状态；交易确认后，智能合约会更新相关记录。

## 2. 使用前准备

使用平台前，请确认：

1. 浏览器已经安装 MetaMask。
2. MetaMask 中已经添加并切换到 Ethereum Sepolia 网络，Chain ID 为 `11155111`。
3. 钱包中有足够的 Sepolia ETH。所有链上写入操作都需要支付 Gas；Funder 还需要支付融资本金，Buyer 需要支付发票票面金额。
4. 使用平台提供的正式访问地址，不要通过来源不明的链接连接钱包。
5. 不要在网页中输入助记词、私钥或 MetaMask 密码。平台只会请求连接钱包、签署登录消息或确认链上交易。

Sepolia ETH 可以通过可信的 Sepolia Faucet 获取。领取前应再次确认 Faucet 所选网络和收款钱包地址，收到测试 ETH 后再开始业务操作。

### 2.1 首次使用推荐顺序

1. 打开平台并连接 MetaMask。
2. 切换到 Sepolia，核对顶部钱包地址和 `Profile` 中的余额。
3. 完成一次 `Sign in`，以便读取业务发票号和已验证交易记录。
4. 进入 `Profile → Manage` 检查角色状态；没有所需角色时先提交申请。
5. 角色获批后，在顶部选择角色，再进入 `Home` 查看待办，或从 `Activity` 开始业务操作。

如果切换了 MetaMask 账户，请从第 2 步重新检查网络、登录状态、角色和余额。

## 3. 钱包连接、登录与角色

### 3.1 连接钱包

首次进入平台时，点击 `Connect` 或 `Connect MetaMask`，在 MetaMask 中选择并授权一个钱包账户。

如果钱包已经处于 Sepolia，连接后平台可能立即请求签署登录消息。消息签名不是链上交易，不会产生 Gas；如果暂时取消，稍后仍可从侧栏或 `Profile` 点击 `Sign in`。

连接钱包后，平台可以：

- 读取该钱包在 Sepolia 上的角色、发票、融资和争议记录；
- 使用该钱包签署交易；
- 显示钱包的 Sepolia ETH 余额。

如果当前网络不是 Sepolia，页面会显示 `Switch network` 或 `Switch to Sepolia`。点击后在 MetaMask 中确认网络切换。

### 3.2 Sign in 的作用

`Sign in` 使用钱包签名验证身份，不会提交链上交易，也不会消耗 Gas。登录后，平台可以读取与该钱包有关的受控业务元数据和已验证交易记录，例如业务发票号。

未登录时仍可读取公开链上数据并执行大部分链上操作，但页面可能只显示链上 `Invoice #`、金额或地址，而不显示业务发票号。Supplier 创建发票前应先登录，否则业务发票号不会保存到后端元数据中。

切换 MetaMask 账户后，原钱包的登录状态会被清除。请根据需要使用新钱包重新 `Sign in`。

### 3.3 角色状态

一个钱包可以同时拥有多个角色。顶部角色选择器用于切换当前工作视图，不会自动授予权限。

- 绿点：该角色已激活，可以发起该角色的新业务操作。
- 红点：该角色尚未激活。
- `Pending`：角色申请已经提交，正在等待管理员批准。
- `Active`：角色已经由管理员批准。
- `Not active`：角色未激活或已被撤销。

角色被撤销后，钱包不能再以该角色发起新的业务，但已经记录在现有发票或融资中的参与关系仍然有效，相关记录仍可查看，并可在系统允许时完成后续操作。

## 4. 角色与职责

| 角色 | 主要职责 |
|---|---|
| Supplier | 创建发票、申请融资、比较并接受报价、查看收款情况 |
| Buyer | 确认或拒绝发票、偿还已融资发票、参与争议 |
| Funder | 浏览融资机会、提交或撤回报价、对被接受的报价放款 |
| Arbitrator | 查看争议和证据哈希，选择系统预定义的裁决结果 |
| Auditor | 只读查看协议汇总、资金流和链上事件 |
| Admin | 批准或撤销参与者角色 |

`Admin` 是部署 `RoleRegistry` 合约的钱包，不通过普通角色申请获得。

## 5. 页面导航

平台有四个主要入口：

- `Home`：显示当前角色、待办事项、相关发票和最近交易。
- `Activity`：办理发票、融资、争议或审计业务。可见栏目会随当前角色变化。
- `Transactions`：查看当前钱包发起的交易及确认状态，并跳转到 Etherscan。
- `Profile`：查看钱包、网络、登录会话、余额和角色状态，并进入角色管理。

桌面端使用左侧导航栏；移动端使用页面底部的四项导航。顶部角色选择器在两种布局中都可使用。

### 5.1 操作按钮为什么会变化

平台只显示当前角色和当前业务阶段允许的操作。例如，发票未确认时不会出现融资申请，报价未被接受时不会出现放款，发票未到期时不会出现逾期操作。

如果预期按钮没有出现，请依次检查：

1. MetaMask 当前账户是否正确；
2. 是否已经切换到 Sepolia；
3. 顶部是否选择了正确角色；
4. 该角色是否为 `Active`，或当前钱包是否已经是该业务的记录参与方；
5. 发票、融资、报价或争议是否处于允许该操作的状态；
6. 报价截止时间、24 小时放款窗口、到期日或 3 天宽限期是否已经满足；
7. 是否存在状态为 `Open` 的争议，导致相关融资操作被冻结。

完成链上交易后，页面数据可能需要数秒刷新。不要仅因为按钮暂时没有变化就重复发送交易。

## 6. 申请和管理角色

### 6.1 参与者申请角色

1. 连接需要申请角色的钱包并切换到 Sepolia。
2. 进入 `Profile`，在 `Participant roles` 区域点击 `Manage`。
3. 找到需要的角色，点击 `Request role`。
4. 在平台的交易确认窗口核对目标合约和预计 Gas。
5. 点击 `Continue to MetaMask`，然后在 MetaMask 中确认交易。
6. 链上确认后，角色状态变为 `Pending`。
7. 等待管理员批准。批准后角色状态变为 `Active`，顶部对应角色显示绿点。

重复申请同一角色会被合约拒绝。已经拥有的角色无需再次申请。

### 6.2 Admin 批准角色

1. 使用 Admin 钱包连接平台，并在顶部选择 `Admin`。
2. 进入 `Profile → Manage`。
3. 在 `Pending requests` 中核对申请钱包和申请角色。
4. 点击 `Approve`，依次在平台确认窗口和 MetaMask 中确认交易。
5. 等待链上确认。申请人的角色随后变为 `Active`。

### 6.3 Admin 撤销角色

在 `Active participant roles` 中找到对应的钱包和角色，点击 `Revoke` 并确认交易。撤销只会阻止该钱包发起需要该角色的新操作，不会删除已经存在的链上记录。

## 7. Supplier 操作

### 7.1 创建发票

创建前应确保：

- Supplier 角色为 `Active`；
- 指定的 Buyer 钱包已经拥有 `Active Buyer` 角色；
- Buyer 地址不是 Supplier 自己的地址；
- Due date 晚于 Issue date，并且晚于当前时间；
- 钱包已登录，以便保存和显示业务发票号。

操作步骤：

1. 在顶部选择 `Supplier`。
2. 进入 `Activity → Invoices`。
3. 在 `Create invoice` 中填写：
   - `Buyer wallet`：买方完整钱包地址；
   - `Invoice number`：企业内部使用的业务发票号；
   - `Face value (ETH)`：买方最终应付的发票票面金额；
   - `Issue date`：发票开具日期；
   - `Due date`：付款到期日；
   - `Document hash (optional)`：可选的 `bytes32` 文档哈希。
4. 如果没有准备文档哈希，可以留空。平台会根据发票号生成一个哈希，但不会上传或保存原始发票文件。
5. 点击 `Submit invoice`。
6. 在平台确认窗口核对目标合约、发送金额和预计 Gas。创建发票本身不转移业务资金，`Amount sent` 应为 `0 ETH`。
7. 点击 `Continue to MetaMask` 并确认交易。
8. 链上确认后，发票状态为 `Awaiting buyer`。

业务发票号保存在后端元数据中；链上保存发票号哈希、参与方、金额、日期和文档哈希。相同参与方和关键字段组合不能重复登记。

### 7.2 申请融资

只有状态为 `Confirmed` 的发票可以申请融资。

1. 进入 `Activity → Financing`。
2. 在 `Ready for financing` 中找到目标发票。
3. 填写：
   - `Funding amount (ETH)`：希望提前获得的融资本金，必须大于 0 且不超过发票票面金额；
   - `Max rate (bps)`：可接受的最高年化利率；
   - `Holdback (bps)`：从融资本金中暂时保留在合约里的比例；
   - `Offer deadline`：资金方提交报价的截止时间，必须晚于当前时间且早于发票到期日。
4. 点击 `Request financing` 并确认交易。
5. 成功后，发票状态变为 `Financing open`，融资状态变为 `Open`。

`bps` 表示基点：`100 bps = 1%`，`600 bps = 6%`，`1000 bps = 10%`。当前合约允许的最高利率不超过 `10000 bps`，Holdback 不超过 `5000 bps`。

### 7.3 查看并接受报价

1. 在 `Activity → Financing → Needs action` 中打开对应融资记录。
2. 比较报价利率和资金方地址。
3. 点击目标报价右侧的 `Accept` 并确认交易。
4. 成功后融资状态变为 `Offer accepted`。

接受报价不会立即收到资金。被选中的 Funder 必须在接受后的 24 小时内完成放款。

### 7.4 取消或关闭融资申请

- 在报价被接受前，Supplier 可以点击 `Cancel request` 取消融资申请。
- 报价截止后，可以点击 `Close expired request` 关闭过期申请。
- 被接受的报价超过 24 小时仍未放款时，可以点击 `Release expired offer`。如果原报价期限仍有效，融资申请会重新开放；否则申请会结束并恢复发票的 `Confirmed` 状态。

争议处于 `Open` 时，这些融资操作会被冻结。

## 8. Buyer 操作

### 8.1 确认或拒绝发票

1. 使用发票中指定的 Buyer 钱包连接平台。
2. 建议先 `Sign in`，以便显示业务发票号。
3. 在顶部选择 `Buyer`，进入 `Activity → Invoices`。
4. 在 `Invoices for your review` 中核对 Supplier、发票号、金额和到期日。
5. 信息正确时点击 `Confirm`；不同意时点击 `Reject`。
6. 在确认窗口和 MetaMask 中完成交易。

确认后状态变为 `Confirmed`，Supplier 可以用该发票申请融资。拒绝后状态变为 `Rejected`，该发票不能继续进入融资流程。确认或拒绝前请认真核对信息。

### 8.2 偿还发票

已放款发票会出现在 `Activity → Financing → Repayments due`。

1. 核对发票、票面金额和当前状态。
2. 点击 `Repay`。按钮会显示需要支付的完整发票票面金额。
3. 在平台确认窗口核对 `Amount sent`，再进入 MetaMask 确认。
4. 等待交易确认，不要在确认过程中重复提交。

没有未解决争议时，合约会立即完成结算：向 Funder 支付本金和利息，向平台 Treasury 支付费用，并将剩余金额与 Holdback 结算给 Supplier。发票进入 `Repaid`，融资进入 `Settled`。

存在未解决争议时，Buyer 仍然可以还款，但资金不会立即分账。发票状态变为 `Repayment deposited`，付款暂存在 `FinancingPool`，等待 Arbitrator 裁决。该状态下不能重复还款。

## 9. Funder 操作

### 9.1 提交报价

1. 使用具有 `Active Funder` 角色的钱包连接平台。
2. 在顶部选择 `Funder`，进入 `Activity → Financing`。
3. 在 `Open opportunities` 中查看融资本金、发票票面金额、最高利率和报价截止时间。
4. 在 `Your annual rate (bps)` 中输入报价利率。报价必须大于 0，且不能高于 Supplier 设置的最高利率。
5. 点击 `Submit offer` 并确认交易。

Supplier 不能用同一个钱包为自己的融资申请报价。单个融资申请最多接受 20 个链上报价。

### 9.2 撤回报价

融资仍为 `Open`、报价仍为 `Active` 且尚未被接受时，可以在 `Your active projects` 中点击 `Withdraw offer`。撤回后报价变为 `Expired`，不能再次被接受。

### 9.3 完成放款

Supplier 接受报价后：

1. 在 `Your active projects` 中找到状态为 `Offer accepted` 的融资。
2. 查看预计的 Supplier upfront、Held back、Interest、Platform fee、Funder repayment 和 Supplier final。
3. 点击 `Fund`。按钮会显示必须发送的融资本金。
4. 在确认窗口核对 `Amount sent`、余额和预计 Gas。
5. 在 MetaMask 中确认交易。

只有被选中的 Funder 可以放款，发送金额必须与融资本金完全一致，并且必须在报价被接受后的 24 小时内完成。

放款后，合约按以下方式处理资金：

- `Holdback = 融资本金 × Holdback 比例`；
- `Supplier upfront = 融资本金 − Holdback`；
- Holdback 暂时保留在 `FinancingPool`；
- 利息按融资本金、报价年利率和从放款日至到期日的天数计算，并在放款确认时锁定。

例如，发票票面金额为 `0.1 ETH`、融资本金为 `0.08 ETH`、Holdback 为 `10%` 时，`0.008 ETH` 暂时保留在合约中，`0.072 ETH` 立即支付给 Supplier。

## 10. 到期、逾期与违约

### 10.1 标记逾期

发票到达 Due date 后仍未还款时，Supplier、Buyer 或该融资的 Funder 可以在融资卡片上点击 `Mark overdue`。成功后：

- 发票状态变为 `Overdue`；
- 融资状态变为 `Overdue`；
- Buyer 仍可以还款。

### 10.2 确认违约

当前宽限期为到期日后的 3 天。超过到期日加宽限期且仍未结算时，业务参与方可以点击 `Declare default`。

违约确认后：

- 发票和融资进入 `Defaulted`；
- 合约中保留的 Holdback 退还给 Funder；
- 页面记录 Funder 的 `Principal loss` 和 `Unpaid interest`；
- 该融资结束，Buyer 不能再通过原流程还款。

如果存在未解决争议，普通逾期和违约操作会被冻结，由 Arbitrator 根据适用状态决定是否 `Confirm default`。

## 11. 争议与证据

### 11.1 谁可以发起争议

以下钱包可以对相关发票发起争议：

- 发票的 Supplier；
- 发票指定的 Buyer；
- 曾经为该发票融资申请提交过报价的 Funder。

发票处于 `Confirmed`、`Financing open`、`Funded`、`Overdue` 或 `Repayment deposited` 时可以发起争议。同一张发票同一时间只能有一个未解决争议。

### 11.2 发起争议

1. 选择相关参与者角色，进入 `Activity → Disputes`。
2. 在 `Open a dispute` 中找到目标发票。
3. 在 `Reason or reason hash` 中输入简短原因，或直接输入合法的 `bytes32` 哈希。
4. 点击 `Open dispute` 并确认交易。
5. 成功后案件状态为 `Open`，与该发票相关的融资操作被冻结。

如果输入普通文字，前端会计算其 Keccak-256 哈希并提交到链上。链上不保存原因原文。

### 11.3 提交证据哈希

1. 在 `Your cases` 中找到状态为 `Open` 的案件。
2. 在 `Evidence note or hash` 中输入证据说明，或输入已有的 `bytes32` 哈希。
3. 点击 `Add evidence` 并确认交易。

系统只在链上保存 evidence hash、提交钱包和提交时间，不保存文件或原始文字。需要仲裁员查看的原始材料应通过双方认可的链下渠道传递，再用链上哈希核对材料是否被修改。

### 11.4 争议期间还款

争议不会免除 Buyer 的付款义务。Buyer 可以正常点击 `Repay` 支付完整票面金额，资金将进入合约托管，发票显示 `Repayment deposited`。只有争议解决后，合约才会继续处理这笔资金。

## 12. Arbitrator 操作

1. 使用具有 `Active Arbitrator` 角色的钱包连接平台。
2. 选择 `Arbitrator`，进入 `Activity → Disputes`。
3. 在 `Cases` 中查看案件状态、发票阶段、发起人、reason hash、evidence hash 和证据提交人。
4. 根据当前业务阶段选择页面提供的裁决按钮。
5. 在确认窗口和 MetaMask 中确认裁决交易。

系统支持三种预定义裁决：

- `Resume workflow`：解除冻结并继续原业务流程。如果 Buyer 的还款已经托管，合约会立即完成自动分账。
- `Cancel financing`：仅适用于融资已经开放但尚未放款的阶段。融资被取消，发票恢复为 `Confirmed`。
- `Confirm default`：适用于已经放款且尚未结算的 `Funded` 或 `Overdue` 阶段。合约执行违约结算并将 Holdback 退还给 Funder。

Arbitrator 不能自行输入收款地址或裁决金额，也不能裁决自己参与的发票。若 Arbitrator 钱包同时是该发票的 Supplier、Buyer 或参与报价的 Funder，合约会因利益冲突拒绝裁决。

## 13. Auditor 操作

Auditor 页面为只读页面，不提供修改业务状态的按钮。

1. 使用具有 `Active Auditor` 角色的钱包连接平台。
2. 建议先 `Sign in`，以便读取业务发票号等元数据。
3. 选择 `Auditor`，进入 `Activity → Audit`。

Audit 包含三个视图：

### 13.1 Overview

显示：

- 发票总数和已还款数量；
- 累计融资金额；
- Buyer 已结算还款；
- 平台费用和 Supplier 收款；
- 发票与融资状态分布；
- 当前读取到的 Sepolia 区块高度。

点击 `Refresh` 可重新读取最新数据。

### 13.2 Cash flow

逐笔查看融资与结算数据，包括：

- Funder invested；
- Supplier upfront；
- Holdback；
- Interest；
- Funder repayment；
- Platform fee；
- Buyer payment；
- Supplier final。

违约记录会显示 Holdback returned、Principal loss 和 Unpaid interest。

### 13.3 Events

按照时间倒序显示五个业务合约的已确认事件。可以：

- 按 Invoices、Financing and offers、Cash flows、Disputes 或 Roles 分类筛选；
- 按事件名、交易哈希或钱包地址搜索；
- 点击 `View transaction on Etherscan` 独立核对交易。

Audit 数据由浏览器通过 Sepolia RPC 实时读取，不依赖后端保存链上业务镜像。首次加载或 RPC 较慢时，需要等待事件扫描完成。

## 14. 交易确认与查询

每次链上写入都经过两次确认：

1. 平台首先显示 `Review transaction`，列出目标合约、发送金额、预计 Gas、预计最高网络费用和钱包余额。
2. 点击 `Continue to MetaMask` 后，MetaMask 显示最终交易信息并请求签名。

如果平台检测到余额不足，会禁用继续按钮。Gas 价格可能在估算后变化，应以 MetaMask 的最终显示为准。

`Transactions` 页面中的状态含义：

| 状态 | 含义 |
|---|---|
| `Awaiting signature` | 等待用户在平台或 MetaMask 中确认 |
| `Confirming` | 交易已提交，正在等待 Sepolia 确认 |
| `Confirmed` | 链上交易成功 |
| `Failed` | 交易提交失败或被合约回退 |
| `Cancelled` | 用户在平台确认窗口或 MetaMask 中取消 |

登录状态下，链上确认后的交易还会由后端验证并保存。如果显示 `Confirmed on-chain · Sync incomplete`，说明链上交易已经成功，只是后端交易记录同步失败。此时应先通过 Etherscan 核对，不要重复提交资金交易。

## 15. 业务状态说明

### 15.1 发票状态

| 状态 | 含义 |
|---|---|
| `Awaiting buyer` | 等待指定 Buyer 确认或拒绝 |
| `Rejected` | Buyer 已拒绝，流程结束 |
| `Confirmed` | Buyer 已确认，可以申请融资 |
| `Financing open` | 融资申请开放中 |
| `Funded` | Funder 已放款，等待 Buyer 还款 |
| `Repaid` | Buyer 已还款并完成结算 |
| `Overdue` | 已过到期日且被标记为逾期 |
| `Repayment deposited` | 争议期间的还款已进入合约托管 |
| `Defaulted` | 已确认违约，流程结束 |

### 15.2 融资状态

| 状态 | 含义 |
|---|---|
| `Open` | 正在接受 Funder 报价 |
| `Offer accepted` | Supplier 已选择报价，等待被选中的 Funder 放款 |
| `Funded` | 已放款，等待 Buyer 还款 |
| `Settled` | 已完成还款和自动分账 |
| `Cancelled` | Supplier 或争议裁决取消融资 |
| `Expired` | 报价或放款窗口过期后关闭 |
| `Overdue` | 已超过发票到期日 |
| `Defaulted` | 已执行违约结算 |

### 15.3 报价与争议状态

| 类型 | 状态 | 含义 |
|---|---|---|
| Offer | `Active` | 可被 Supplier 接受，也可由 Funder 撤回 |
| Offer | `Accepted` | 已被 Supplier 选择，等待放款 |
| Offer | `Expired` | 已撤回、被其他报价替代或窗口已经结束 |
| Dispute | `Open` | 争议处理中，相关融资操作被冻结 |
| Dispute | `Resolved` | Arbitrator 已完成裁决 |

## 16. 移动端使用

平台采用响应式布局，可以在手机浏览器中使用：

- 主导航显示在页面底部；
- 业务卡片自动改为单列；
- 顶部仍可切换角色、查看钱包地址和网络状态；
- MetaMask Mobile 用户需要在 MetaMask 内置浏览器中打开平台，或使用支持钱包连接的浏览器环境。

提交交易后应等待状态更新，不要因为移动网络延迟而连续点击同一按钮。需要核对交易时，可从 `Transactions` 或业务卡片进入 Etherscan。

## 17. 常见问题

| 问题 | 处理方法 |
|---|---|
| 页面提示未安装 MetaMask | 安装并启用 MetaMask，然后重新打开页面 |
| 页面要求切换网络 | 点击 `Switch network`，在 MetaMask 中切换到 Sepolia |
| 看不到业务发票号 | 使用当前钱包 `Sign in`；Supplier、指定 Buyer 和 Active Auditor 才能读取相应元数据 |
| 切换钱包后变成 Signed out | 这是正常的安全行为，请使用新钱包重新登录 |
| 角色显示红点或 Not active | 进入 `Profile → Manage` 申请角色，并等待 Admin 批准 |
| 角色一直显示 Pending | 联系 Admin 检查并批准链上申请 |
| 交易按钮不可用 | 检查钱包连接、Sepolia 网络、角色状态、业务状态和合约配置 |
| MetaMask 提示余额不足 | 获取足够的 Sepolia ETH，并预留交易金额和 Gas |
| 交易显示 Confirming 很久 | 在 Etherscan 查询交易哈希，检查 Sepolia 和 RPC 状态 |
| 页面没有立即更新 | 等待数秒后刷新数据；先核对 Etherscan，避免重复付款或放款 |
| Confirmed on-chain · Sync incomplete | 链上交易已经成功，仅后端记录同步失败；不要重复提交交易 |
| 发票号显示成 Invoice # | 当前钱包未登录或无权读取该发票的链下元数据 |
| 证据只显示哈希 | 当前系统只保存链上哈希、提交者和时间，不保存原文或文件 |
| 融资操作被冻结 | 检查是否存在状态为 Open 的争议，等待 Arbitrator 裁决 |
| 无法裁决争议 | 确认 Arbitrator 角色已激活，并确认该钱包不是发票或融资参与方 |
| Audit 加载较慢 | 等待实时链上事件扫描完成，或检查 Sepolia RPC 后点击 Refresh |

## 18. 安全使用建议

- 每次交易都核对操作名称、目标合约、发送金额和钱包账户。
- Buyer 还款和 Funder 放款必须等待上一笔交易明确成功或失败后再操作。
- 对金额较大的操作，先通过 Etherscan 核对合约地址和当前状态。
- 不要把普通文本证据误认为链上可恢复文件；提交哈希前应自行保留原始材料。
- 不要向合约地址直接转账。业务资金必须通过页面提供的 `Fund` 或 `Repay` 操作发送。
- 如果页面状态与 Etherscan 不一致，以已确认的链上交易和合约状态为准，并在重新提交前联系平台管理员。
