# 6 分钟单发票业务链演示流程

本文是面向第一次接触系统的录制操作手册。整段视频只使用一张发票，依次演示：

`创建发票 → Buyer 确认 → 申请融资 → Funder 报价 → Supplier 接受 → Funder 放款 → Buyer 发起争议并提交证据 → Buyer 在争议中还款 → Arbitrator 裁决 → 自动分账 → Auditor 审计`

这条链同时覆盖正常融资和争议结算，不再准备第二张发票。部署、角色申请、角色审批、到期等待和异常测试不放进 6 分钟正片。

## 1. 角色分配

| 钱包 | 角色 | 本次操作 |
|---|---|---|
| A | Supplier | 创建发票、申请融资、接受报价 |
| B | Buyer | 确认发票、发起争议、提交证据、还款 |
| C | Funder | 报价、放款、接收本息 |
| D | Arbitrator + Auditor | 裁决争议、审计完整业务 |
| admin | Admin | 录制前完成角色审批，正片不操作 |

D 可以同时拥有 Arbitrator 和 Auditor 两个角色，但不能是本张发票的 Supplier、Buyer 或 Funder，否则不能裁决该争议。

## 2. 录制前必须准备好

正式录制前逐项确认：

- 五份合约已经部署并完成地址配置；
- 前端、后端和 Sepolia RPC 正常运行；
- A、B、C、D、admin 都使用 Sepolia 网络；
- admin 已经批准 A 的 Supplier、B 的 Buyer、C 的 Funder、D 的 Arbitrator 和 Auditor；
- A、B、C、D 对应角色在顶部列表中显示绿点；
- A、B、C、D 都准备了足够的 Sepolia ETH；
- A、B、C、D 的钱包均能正常连接；不需要预先逐个 `Sign in`；
- 数据库中没有使用过本次发票号 `INV-DEMO-001`；
- 浏览器、MetaMask 弹窗和录屏区域已经调整好。

建议余额：A 和 D 至少 `0.02 ETH`，B 至少 `0.07 ETH`，C 至少 `0.06 ETH`。B 需要支付 `0.05 ETH` 票款，C 需要支付 `0.04 ETH` 融资本金，另外都要预留 Gas。

不要在录制过程中清空数据库。业务发票号保存在后端元数据中，清空数据库会导致页面只能显示链上 ID 或金额。

## 3. 固定使用的演示数据

| 字段 | 输入值 |
|---|---|
| Invoice number | `INV-DEMO-001` |
| Buyer wallet | B 的完整钱包地址 |
| Face value | `0.05` ETH |
| Issue date | 录制当天 |
| Due date | 录制当天至少 7 天后 |
| Document hash | 留空，由前端自动生成 |
| Funding amount | `0.04` ETH |
| Maximum rate | `800` bps，即 8% |
| Holdback | `1000` bps，即融资本金的 10% |
| Offer rate | `600` bps，即 6% |
| Offer deadline | 当前时间之后 1 天，且早于 Due date |
| Dispute reason | `Delivery evidence does not match the purchase order` |
| Evidence note | `Buyer evidence: delivery receipt reference DEMO-001 is inconsistent` |

放款时，C 支付 `0.04 ETH`，其中 `0.004 ETH` 作为 Holdback 留在合约，A 首笔收到 `0.036 ETH`。

## 4. 每次切换钱包时都这样做

从 A 切换到 B、C 或 D 时，固定执行以下步骤：

1. 在 MetaMask 中选择目标账户；
2. 等待页面右上角的钱包短地址发生变化；
3. 在顶部角色列表选择本步骤要求的角色；
4. 确认该角色前面是绿点；
5. 再进入 `Activity` 执行业务操作。

切换 MetaMask 账户会自动清除上一账户的后端登录会话，这是正常现象。链上查询和交易不要求 `Sign in`；未登录时仍可完成确认、融资、报价、放款、争议、还款和裁决，只是部分卡片会显示金额或链上 ID，而不显示业务发票号，交易也不会保存到后端历史。

本次视频只在三个位置登录：

1. A 创建发票前登录，用于保存 `INV-DEMO-001` 并绑定链上 invoiceId；
2. B 第一次确认发票前登录，让观众看到 Buyer 端也能读取相同发票号；
3. D 完成裁决后、进入 Auditor 页面前登录，让 Auditor 读取全局业务发票号。

C 不需要登录。A、B 后续再次切回时也不需要重新登录，可根据金额、状态、参与钱包和链上 ID 找到同一业务。

每次发送交易时：

1. 先阅读应用弹出的确认摘要；
2. 核对目标合约、发送金额和预计 Gas；
3. 点击继续后，在 MetaMask 中确认；
4. 等待页面显示成功提示和新状态；
5. 交易等待期间不要重复点击按钮。

## 5. 六分钟时间安排

Sepolia 等待确认的部分可以剪掉，但每笔交易保留“点击操作、确认摘要、MetaMask 确认、最终状态”中的关键画面。

| 时间 | 钱包/角色 | 操作 |
|---:|---|---|
| 0:00–0:20 | 旁白 | 说明五个角色已经由 admin 授权，本次只演示一张发票 |
| 0:20–0:50 | A / Supplier | 创建 `INV-DEMO-001` |
| 0:50–1:10 | B / Buyer | 确认发票 |
| 1:10–1:40 | A / Supplier | 发起融资申请 |
| 1:40–2:00 | C / Funder | 提交 6% 报价 |
| 2:00–2:20 | A / Supplier | 接受 C 的报价 |
| 2:20–2:55 | C / Funder | 放款并展示 Holdback 和 Supplier 首笔到账 |
| 2:55–3:40 | B / Buyer | 打开争议并提交 Evidence hash |
| 3:40–4:10 | B / Buyer | 在争议期间还款，展示资金托管 |
| 4:10–4:50 | D / Arbitrator | 查看证据并执行 `Resume workflow` |
| 4:50–5:40 | D / Auditor | 查看 Overview、Cash flow 和 Events |
| 5:40–6:00 | 旁白 | 总结发票、融资、争议和资金最终状态 |

## 6. 正片详细操作

### 第一步：A 创建发票

1. MetaMask 切换到 A。
2. 点击 `Sign in` 并完成一次消息签名。这个签名不消耗 Gas。
3. 顶部选择 `Supplier`，确认是绿点。
4. 点击底部或左侧导航的 `Activity`。
5. 选择 `Invoices`。
6. 在 `Create invoice` 表单填写：
   - `Buyer wallet`：B 的完整地址；
   - `Invoice number`：`INV-DEMO-001`；
   - `Face value (ETH)`：`0.05`；
   - `Issue date`：当天；
   - `Due date`：至少 7 天后；
   - `Document hash`：留空。
7. 点击 `Submit invoice`。
8. 在确认摘要中指出这次不转业务 ETH，只写入发票核心信息和哈希。
9. 在 MetaMask 中确认交易。

成功后应看到：

- 页面显示业务发票号 `INV-DEMO-001`；
- 发票状态为 `Awaiting buyer`；
- Buyer 地址是 B；
- 发票金额是 `0.05 ETH`。

旁白建议：发票原始编号保存在受控业务元数据中，链上保存编号哈希、金额、参与方、日期和文档哈希。

### 第二步：B 确认发票

1. 按第 4 节的方法切换到 B。
2. 点击 `Sign in` 并完成一次消息签名。
3. 顶部选择 `Buyer`。
4. 进入 `Activity → Invoices`。
5. 在待审核发票中找到 `INV-DEMO-001`。
6. 核对 Supplier、金额和 Due date。
7. 点击 `Confirm`，不要点击 `Reject`。
8. 在 MetaMask 中确认交易。

成功后发票状态应变为 `Confirmed`。

旁白建议：只有发票指定的 Buyer 可以确认；没有 Buyer 确认，Supplier 不能用这张发票融资。

### 第三步：A 发起融资

1. 切换回 A，顶部选择 `Supplier`。
2. 进入 `Activity → Financing`。
3. A 此时不必重新登录；在 `Ready for financing` 中找到面值 `0.05 ETH` 的已确认发票。
4. 填写：
   - `Funding amount (ETH)`：`0.04`；
   - `Max rate (bps)`：`800`；
   - `Holdback (bps)`：`1000`；
   - `Offer deadline`：当前时间之后 1 天。
5. 点击 `Request financing` 并确认交易。

成功后应看到：

- 融资状态为 `Open`；
- 发票状态为 `Financing open`；
- 页面显示申请金额、最高 APR 和截止时间。

旁白建议：Supplier 申请提前获得 `0.04 ETH`，并同意保留 10% Holdback 作为风险缓冲。

### 第四步：C 提交报价

1. 切换到 C，顶部选择 `Funder`。
2. 进入 `Activity → Financing`。
3. C 不需要登录；在 `Open opportunities` 找到 Funding amount 为 `0.04 ETH`、Invoice value 为 `0.05 ETH` 的申请。
4. 在 `Your annual rate (bps)` 输入 `600`。
5. 点击 `Submit offer` 并确认交易。

成功后应看到报价为 `Active`，APR 为 `6.00%`。

旁白建议：报价 6% 没有超过 Supplier 设置的最高 8%，因此可以提交。

### 第五步：A 接受报价

1. 切换回 A，选择 `Supplier`。
2. 进入 `Activity → Financing`。
3. 在 `Needs action` 找到金额 `0.04 ETH` 和 C 的 6% 报价。
4. 点击报价右侧的 `Accept`。
5. 确认交易。

成功后融资状态应为 `Offer accepted`。

旁白建议：报价被接受后，只有被选中的 C 可以在 24 小时窗口内放款。

### 第六步：C 放款

1. 切换到 C，选择 `Funder`。
2. 进入 `Activity → Financing`。
3. 在 `Your active projects` 找到已接受的 `0.04 ETH` 项目。
4. 先展示卡片中的预计金额拆分。
5. 点击 `Fund 0.04 ETH`。
6. 在确认摘要和 MetaMask 中核对发送金额确实是 `0.04 ETH`。
7. 确认交易。

成功后应看到：

- 发票状态为 `Funded`；
- 融资状态为 `Funded`；
- C 显示 `Invested 0.04 ETH`；
- A 首笔收到 `0.036 ETH`；
- `0.004 ETH` Holdback 继续留在 FinancingPool。

### 第七步：B 发起争议

争议必须在放款成功以后、还款以前发起，这样才能继续演示争议还款托管。

1. 切换到 B，选择 `Buyer`。
2. 进入 `Activity`，选择 `Disputes`。
3. B 此时不必重新登录；在 `Open a dispute` 中找到状态为 `Funded`、金额为 `0.05 ETH` 的发票。该卡片可能显示链上 `Invoice #`，这是正常的。
4. 在 `Reason or reason hash` 输入：

   `Delivery evidence does not match the purchase order`

5. 点击 `Open dispute` 并确认交易。
6. 等待 Case 出现在 `Your cases`，状态应为 `Open`。

此时融资相关操作被冻结。接着提交一条证据：

1. 在该 Case 的 `Evidence note or hash` 输入：

   `Buyer evidence: delivery receipt reference DEMO-001 is inconsistent`

2. 点击 `Add evidence` 并确认交易。
3. 成功后，Case 中应显示一条 Evidence hash 和 B 的钱包短地址。

证据哈希如何模拟：

- 演示时直接输入上述普通文字即可；
- 前端会使用 Keccak-256 自动把文字转换成 `bytes32`；
- 链上只保存 Evidence hash，不保存这段原文；
- 也可以输入 `0x` 加 64 个十六进制字符，但没有必要手工生成。

录屏时保留 B 输入证据文字以及提交后出现 Evidence hash 的两个画面。后面 D 看到的是同一条链上 Evidence hash，而不是原始文字。

旁白建议：真实业务中证据文件通过受控的链下渠道交给 Arbitrator，链上 Evidence hash 用于核对文件是否被替换。当前演示版尚未实现证据文件上传和原文查看，只实现提交者、时间和内容哈希的链上存证。

### 第八步：B 在争议期间还款

1. B 保持 `Buyer` 角色。
2. 从 `Disputes` 切换到 `Financing`。
3. 在 `Repayments due` 找到面值 `0.05 ETH`、状态为 `Funded` 的发票；未登录时卡片可能不显示 `INV-DEMO-001`。
4. 点击 `Repay 0.05 ETH`。
5. 在确认摘要和 MetaMask 中核对金额为 `0.05 ETH`。
6. 确认交易。

因为争议仍然是 `Open`，这笔钱不会立即分给 A、C 和 Treasury。成功后应看到：

- 发票状态为 `Repayment deposited`；
- 页面出现 `Buyer payment is held while the dispute is open`；
- Case 仍为 `Open`；
- `0.05 ETH` 由 FinancingPool 托管，Buyer 不能重复还款。

旁白建议：Buyer 可以在争议期间履行付款义务，但合约会冻结分账，等待 Arbitrator 裁决。

### 第九步：D 裁决争议并完成结算

1. 切换到 D。
2. 顶部选择 `Arbitrator`，确认是绿点。
3. 此时不需要 `Sign in`；进入 `Activity → Disputes`。
4. 在 `Cases` 中找到刚才的 Case。
5. 展示以下信息：
   - Case 状态是 `Open`；
   - Invoice stage 是 `Repayment deposited`；
   - Opened by 是 B；
   - 页面存在 B 提交的 Evidence hash。
6. 点击 `Resume workflow`。
7. 在 MetaMask 中确认裁决交易。

成功后应看到：

- Case 状态变为 `Resolved`；
- Outcome 为 `Resume`；
- 发票状态变为 `Repaid`；
- 融资状态变为 `Settled`；
- 托管资金自动向 C、A 和 Treasury 分账。

本阶段只显示 `Resume workflow` 是正确的，因为 Buyer 已经把还款存入托管。另两种预定义裁决 `Cancel financing` 和 `Confirm default` 只会在适用的业务阶段显示。Arbitrator 不能输入任意收款地址或任意金额。

Arbitrator 页面会直接调用链上的 `getEvidenceCount` 和 `getEvidence`，因此即使 D 没有后端登录，也能看到 Evidence hash 和提交者钱包。D 看不到原始证据文字或文件；本次演示的裁决依据是前面镜头中展示的链下文字，其哈希已经被链上记录。

### 第十步：D 切换 Auditor 审计

1. 不切换 MetaMask 钱包，继续使用 D。
2. 先点击 `Sign in`，让后端确认 D 的钱包身份并返回 Auditor 可读的业务发票元数据。
3. 顶部角色从 `Arbitrator` 改为 `Auditor`。
4. 进入 `Activity → Audit`。
5. 在 `Overview` 展示：
   - Invoice 数量；
   - Total funded；
   - Buyer repayments；
   - Platform fees。
6. 切换到 `Cash flow`，找到 `INV-DEMO-001`，展示：
   - Funder invested；
   - Supplier upfront；
   - Holdback；
   - Interest；
   - Funder repayment；
   - Platform fee；
   - Buyer payment；
   - Supplier final。
7. 切换到 `Events`，选择 `Disputes` 或 `Cash flows` 分类。
8. 展示 `DisputeOpened`、`EvidenceSubmitted`、`RepaymentDeposited`、`DisputeResolved` 和最终结算相关事件。
9. 打开其中一笔 `View transaction on Etherscan` 链接即可，不需要逐笔打开。

旁白建议：Auditor 能读取完整状态、资金流、区块和交易链接，但页面没有修改业务状态的按钮。

## 7. 六分钟内不演示的内容

- 角色申请和 admin 逐项审批；
- 合约部署和环境变量配置；
- Buyer Reject、Supplier Cancel、Funder Withdraw；
- 报价过期和 24 小时放款窗口过期；
- Overdue、三天宽限期和 Default 的现场等待；
- `Cancel financing` 和 `Confirm default` 两种其他裁决的实际执行；
- 错误钱包、错误金额、重复还款等失败交易；
- 每一笔交易都打开 Etherscan；
- 数据库、API 和源代码说明。

上述能力可以用自动化测试结果、状态机图或历史记录作为补充证据，不要挤占主业务链时间。

## 8. 常见问题和处理

### 页面没有出现目标发票

- 检查 MetaMask 是否切到了正确钱包；
- 检查顶部当前角色是否正确且显示绿点；
- 等待几秒后刷新页面；
- 确认上一笔交易已经成功，而不是仍在确认中。

### 页面显示金额而不是 `INV-DEMO-001`

- 确认钱包已经 `Sign in`；
- 确认后端正在运行；
- 确认没有在创建发票后清空数据库；
- 刷新页面，让后端重新读取 metadata 与链上 invoiceId 的绑定。

### MetaMask 已经确认，但页面没有更新

- 不要再次点击原按钮；
- 等待 Sepolia 出块后刷新页面；
- 在 `Transactions` 或 Etherscan 检查交易是否成功。

### D 看不到 Case

- 确认 D 的 Arbitrator 角色已经由 admin 批准；
- 确认顶部选择的是 `Arbitrator`；
- 确认 B 的 `Open dispute` 交易已经成功；
- 确认 D 没有参与这张发票的 Supplier、Buyer 或 Funder 身份。

### Auditor 看不到发票号

- 确认 D 已完成 `Sign in`；
- 确认 D 的 Auditor 角色是 Active；
- 确认 `INV-DEMO-001` 的 metadata 没有被删除；
- 刷新页面后重新进入 `Activity → Audit`。

## 9. 演示完成标准

视频结束时确认以下结果即可：

- 发票完成 `Awaiting buyer → Confirmed → Financing open → Funded → Repayment deposited → Repaid`；
- 融资完成 `Open → Offer accepted → Funded → Settled`；
- C 的放款、Holdback 和 A 的首笔到账清楚可见；
- B 成功打开争议并提交 Evidence hash；
- B 的争议还款先进入托管，没有立即分账；
- D 使用预定义的 `Resume` 裁决后完成自动分账；
- D 切换到 Auditor 后能看到 `INV-DEMO-001` 的资金流和链上事件；
- Auditor 没有业务写入操作。

达到以上结果即可结束演示，不需要再创建第二张发票。
