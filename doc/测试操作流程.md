# 6 分钟单发票业务链演示流程

本文是面向第一次接触系统的录制操作手册。整段视频只使用一张发票，依次演示：

`A 申请 Supplier → Admin 批准 → 创建发票 → Buyer 确认 → 申请融资 → Funder 报价 → Supplier 接受 → Funder 放款 → Buyer 发起争议并提交证据 → Buyer 在争议中还款 → Arbitrator 裁决 → 自动分账 → Auditor 审计`

这条链同时覆盖一次角色授权、正常融资和争议结算，不再准备第二张发票。部署、其余角色的逐项授权、到期等待和异常测试不放进 6 分钟正片。

## 1. 角色分配

| 钱包 | 角色 | 本次操作 |
|---|---|---|
| A | Supplier | 创建发票、申请融资、接受报价 |
| B | Buyer | 桌面确认发票；在开始演示 Dispute 时切入移动视图，连续提交争议、证据并还款 |
| C | Funder | 报价、放款、接收本息 |
| D | Arbitrator + Auditor | 在移动视图裁决争议，准备展示 Audit 时恢复桌面并完成审计 |
| admin | Admin | 正片批准 A 的 Supplier；其余角色录制前批准 |

D 可以同时拥有 Arbitrator 和 Auditor 两个角色，但不能是本张发票的 Supplier、Buyer 或 Funder，否则不能裁决该争议。

## 2. 录制前必须准备好

正式录制前逐项确认：

- 五份合约已经部署并完成地址配置；
- 前端、后端和 Sepolia RPC 正常运行；
- A、B、C、D、admin 都使用 Sepolia 网络；
- admin 已经批准 B 的 Buyer、C 的 Funder、D 的 Arbitrator 和 Auditor；
- A 的 Supplier 在录制开始时必须是 Inactive、显示红点，并且没有尚未处理的 Pending 申请；如已激活，录制前由 admin 撤销；
- B、C、D 对应角色在顶部列表中显示绿点；admin 钱包能够进入 Admin 视图；
- A、B、C、D 都准备了足够的 Sepolia ETH；
- A、B、C、D 的钱包均能正常连接；不需要预先逐个 `Sign in`；
- 数据库中没有使用过本次发票号 `INV-DEMO-001`；
- 浏览器、MetaMask 弹窗和录屏区域已经调整好；
- Chrome 或 Edge 的 DevTools 已测试可用，移动视图预设为 `390 × 844`，页面没有横向溢出。

建议余额：A 和 D 至少 `0.02 ETH`，B 至少 `0.07 ETH`，C 至少 `0.06 ETH`。B 需要支付 `0.05 ETH` 票款，C 需要支付 `0.04 ETH` 融资本金，另外都要预留 Gas。

不要在录制过程中清空数据库。业务发票号保存在后端元数据中，清空数据库会导致页面只能显示链上 ID 或金额。

## 3. 固定使用的演示数据

| 字段 | 输入值 |
|---|---|
| Invoice number | `INV-DEMO-001` |
| Buyer wallet | B 的完整钱包地址 |
| Face value | `0.05` ETH |
| Issue date | 录制当天 |
| Due date | 录制当天至少 7 天后 |
| Document hash | 留空，由前端自动生成 |
| Funding amount | `0.04` ETH |
| Maximum rate | `800` bps，即 8% |
| Holdback | `1000` bps，即融资本金的 10% |
| Offer rate | `600` bps，即 6% |
| Offer deadline | 当前时间之后 1 天，且早于 Due date |
| Dispute reason | `Delivery evidence does not match the purchase order` |
| Evidence note | `Buyer evidence: delivery receipt reference DEMO-001 is inconsistent` |

放款时，C 支付 `0.04 ETH`，其中 `0.004 ETH` 作为 Holdback 留在合约，A 首笔收到 `0.036 ETH`。
## 4. 正片详细操作

### 第一步：A 申请 Supplier，admin 批准

这一步只演示一个角色的完整授权，其他角色已经在录制前批准。

1. MetaMask 切换到 A，确认顶部 `Supplier` 前是红点。
2. 进入 `Profile → Manage`。
3. 在 Supplier 角色上点击 `Request role`。
4. 在 MetaMask 中确认 `requestRole` 交易。
5. 交易成功后，页面应显示该申请为 Pending；此时还不能创建发票。
6. MetaMask 切换到 admin，顶部选择 `Admin`。
7. 进入 `Profile → Manage`，在 `Pending requests` 中找到 A 的 Supplier 申请。
8. 点击 `Approve`，在 MetaMask 中确认 `approveRole` 交易。
9. 交易成功后切回 A，确认顶部 Supplier 由红点变为绿点。

旁白建议：角色申请和批准都记录在 RoleRegistry 中。只有 Admin 批准后的 Active Supplier 才能创建发票；顶部绿点表示当前钱包已获得该角色。

为了控制时间，Sepolia 等待确认的过程可以剪掉，但应保留 A 的红点、Pending、admin 点击 Approve 和最终绿点四个画面。

### 第二步：A 创建发票

1. 保持 A 钱包和 `Supplier` 角色。
2. 点击 `Sign in` 并完成一次消息签名。这个签名不消耗 Gas。
3. 顶部选择 `Supplier`，确认是绿点。
4. 点击底部或左侧导航的 `Activity`。
5. 选择 `Invoices`。
6. 在 `Create invoice` 表单填写：
   - `Buyer wallet`：B 的完整地址；
   - `Invoice number`：`INV-DEMO-001`；
   - `Face value (ETH)`：`0.05`；
   - `Issue date`：当天；
   - `Due date`：至少 7 天后；
   - `Document hash`：留空。
7. 点击 `Submit invoice`。
8. 在确认摘要中指出这次不转业务 ETH，只写入发票核心信息和哈希。
9. 在 MetaMask 中确认交易。

成功后应看到：

- 页面显示业务发票号 `INV-DEMO-001`；
- 发票状态为 `Awaiting buyer`；
- Buyer 地址是 B；
- 发票金额是 `0.05 ETH`。

旁白建议：发票原始编号保存在受控业务元数据中，链上保存编号哈希、金额、参与方、日期和文档哈希。

### 第三步：B 确认发票

1. 按第 4 节的方法切换到 B。
2. 保持桌面视图，点击 `Sign in` 并完成一次消息签名。
3. 顶部选择 `Buyer`。
4. 进入 `Activity → Invoices`。
5. 在待审核发票中找到 `INV-DEMO-001`。
6. 核对 Supplier、金额和 Due date。
7. 点击 `Confirm`，不要点击 `Reject`。
8. 在 MetaMask 中确认交易。

成功后发票状态应变为 `Confirmed`。

旁白建议：只有发票指定的 Buyer 可以确认；没有 Buyer 确认，Supplier 不能用这张发票融资。

### 第四步：A 发起融资

1. 切换回 A，顶部选择 `Supplier`。
2. 进入 `Activity → Financing`。
3. A 此时不必重新登录；在 `Ready for financing` 中找到面值 `0.05 ETH` 的已确认发票。
4. 填写：
   - `Funding amount (ETH)`：`0.04`；
   - `Max rate (bps)`：`800`；
   - `Holdback (bps)`：`1000`；
   - `Offer deadline`：当前时间之后 1 天。
5. 点击 `Request financing` 并确认交易。

成功后应看到：

- 融资状态为 `Open`；
- 发票状态为 `Financing open`；
- 页面显示申请金额、最高 APR 和截止时间。

旁白建议：Supplier 申请提前获得 `0.04 ETH`，并同意保留 10% Holdback 作为风险缓冲。

### 第五步：C 提交报价

1. 切换到 C，顶部选择 `Funder`。
2. 进入 `Activity → Financing`。
3. C 不需要登录；在 `Open opportunities` 找到 Funding amount 为 `0.04 ETH`、Invoice value 为 `0.05 ETH` 的申请。
4. 在 `Your annual rate (bps)` 输入 `600`。
5. 点击 `Submit offer` 并确认交易。

成功后应看到报价为 `Active`，APR 为 `6.00%`。

旁白建议：报价 6% 没有超过 Supplier 设置的最高 8%，因此可以提交。

### 第六步：A 接受报价

1. 切换回 A，选择 `Supplier`。
2. 进入 `Activity → Financing`。
3. 在 `Needs action` 找到金额 `0.04 ETH` 和 C 的 6% 报价。
4. 点击报价右侧的 `Accept`。
5. 确认交易。

成功后融资状态应为 `Offer accepted`。

旁白建议：报价被接受后，只有被选中的 C 可以在 24 小时窗口内放款。

### 第七步：C 放款

1. 切换到 C，选择 `Funder`。
2. 进入 `Activity → Financing`。
3. 在 `Your active projects` 找到已接受的 `0.04 ETH` 项目。
4. 先展示卡片中的预计金额拆分。
5. 点击 `Fund 0.04 ETH`。
6. 在确认摘要和 MetaMask 中核对发送金额确实是 `0.04 ETH`。
7. 确认交易。

成功后应看到：

- 发票状态为 `Funded`；
- 融资状态为 `Funded`；
- C 显示 `Invested 0.04 ETH`；
- A 首笔收到 `0.036 ETH`；
- `0.004 ETH` Holdback 继续留在 FinancingPool。

### 第八步：B 发起争议

争议必须在放款成功以后、还款以前发起，这样才能继续演示争议还款托管。

1. 切换到 B，选择 `Buyer`。
2. 按 `F12` 和 `Ctrl + Shift + M`，进入本次演示唯一的 `390 × 844` 手机视图片段。
3. 停留两秒，展示顶部 Buyer 角色、单列卡片和底部四项导航，确认页面没有横向滚动条。
4. 从底部进入 `Activity`，选择 `Disputes`。
5. B 此时不必重新登录；在 `Open a dispute` 中找到状态为 `Funded`、金额为 `0.05 ETH` 的发票。该卡片可能显示链上 `Invoice #`，这是正常的。
6. 在 `Reason or reason hash` 输入：

   `Delivery evidence does not match the purchase order`

7. 点击 `Open dispute` 并确认交易。
8. 等待 Case 出现在 `Your cases`，状态应为 `Open`。

此时融资相关操作被冻结。接着提交一条证据：

1. 在该 Case 的 `Evidence note or hash` 输入：

   `Buyer evidence: delivery receipt reference DEMO-001 is inconsistent`

2. 点击 `Add evidence` 并确认交易。
3. 成功后，Case 中应显示一条 Evidence hash 和 B 的钱包短地址。

证据哈希如何模拟：

- 演示时直接输入上述普通文字即可；
- 前端会使用 Keccak-256 自动把文字转换成 `bytes32`；
- 链上只保存 Evidence hash，不保存这段原文；
- 也可以输入 `0x` 加 64 个十六进制字符，但没有必要手工生成。

录屏时保留 B 输入证据文字以及提交后出现 Evidence hash 的两个画面。后面 D 看到的是同一条链上 Evidence hash，而不是原始文字。

旁白建议：真实业务中证据文件通过受控的链下渠道交给 Arbitrator，链上 Evidence hash 用于核对文件是否被替换。当前演示版尚未实现证据文件上传和原文查看，只实现提交者、时间和内容哈希的链上存证。

### 第九步：B 在争议期间还款

1. B 保持 `Buyer` 角色和手机视图。
2. 从 `Disputes` 切换到 `Financing`。
3. 在 `Repayments due` 找到面值 `0.05 ETH`、状态为 `Funded` 的发票；未登录时卡片可能不显示 `INV-DEMO-001`。
4. 点击 `Repay 0.05 ETH`。
5. 在确认摘要和 MetaMask 中核对金额为 `0.05 ETH`。
6. 确认交易。

因为争议仍然是 `Open`，这笔钱不会立即分给 A、C 和 Treasury。成功后应看到：

- 发票状态为 `Repayment deposited`；
- 页面出现 `Buyer payment is held while the dispute is open`；
- Case 仍为 `Open`；
- `0.05 ETH` 由 FinancingPool 托管，Buyer 不能重复还款。

旁白建议：Buyer 可以在争议期间履行付款义务，但合约会冻结分账，等待 Arbitrator 裁决。

### 第十步：D 裁决争议并完成结算

1. 保持 `390 × 844` 移动视图，在 MetaMask 中切换到 D。
2. 顶部选择 `Arbitrator`，确认是绿点。
3. 此时不需要 `Sign in`；进入 `Activity → Disputes`。
4. 在 `Cases` 中找到刚才的 Case。
5. 展示以下信息：
   - Case 状态是 `Open`；
   - Invoice stage 是 `Repayment deposited`；
   - Opened by 是 B；
   - 页面存在 B 提交的 Evidence hash。
6. 点击 `Resume workflow`。
7. 在 MetaMask 中确认裁决交易。

成功后应看到：

- Case 状态变为 `Resolved`；
- Outcome 为 `Resume`；
- 发票状态变为 `Repaid`；
- 融资状态变为 `Settled`；
- 托管资金自动向 C、A 和 Treasury 分账。

本阶段只显示 `Resume workflow` 是正确的，因为 Buyer 已经把还款存入托管。另两种预定义裁决 `Cancel financing` 和 `Confirm default` 只会在适用的业务阶段显示。Arbitrator 不能输入任意收款地址或任意金额。

Arbitrator 页面会直接调用链上的 `getEvidenceCount` 和 `getEvidence`，因此即使 D 没有后端登录，也能看到 Evidence hash 和提交者钱包。D 看不到原始证据文字或文件；本次演示的裁决依据是前面镜头中展示的链下文字，其哈希已经被链上记录。

### 第十一步：D 切换 Auditor 审计

1. 不切换 MetaMask 钱包，继续使用 D。
2. 按 `Ctrl + Shift + M` 恢复桌面视图并关闭 DevTools；这是本次唯一一次从移动端恢复桌面端。
3. 先点击 `Sign in`，让后端确认 D 的钱包身份并返回 Auditor 可读的业务发票元数据。
4. 顶部角色从 `Arbitrator` 改为 `Auditor`。
5. 进入 `Activity → Audit`。
6. 在 `Overview` 展示：
   - Invoice 数量；
   - Total funded；
   - Buyer repayments；
   - Platform fees。
7. 切换到 `Cash flow`，找到 `INV-DEMO-001`，展示：
   - Funder invested；
   - Supplier upfront；
   - Holdback；
   - Interest；
   - Funder repayment；
   - Platform fee；
   - Buyer payment；
   - Supplier final。
8. 切换到 `Events`，选择 `Disputes` 或 `Cash flows` 分类。
9. 展示 `DisputeOpened`、`EvidenceSubmitted`、`RepaymentDeposited`、`DisputeResolved` 和最终结算相关事件。
10. 打开其中一笔 `View transaction on Etherscan` 链接即可，不需要逐笔打开。

旁白建议：Auditor 能读取完整状态、资金流、区块和交易链接，但页面没有修改业务状态的按钮。

## 5. 中文旁白脚本

以下内容可以直接照读。交易等待时可以继续旁白，Sepolia 确认时间过长的部分后期剪掉，不要逐项朗读钱包地址和表单字段。

### 开场

> 这是一个运行在 Ethereum Sepolia 测试网上的应收账款融资 DApp。我们会用一张发票，在六分钟内展示角色授权、发票确认、融资报价、放款、争议托管、仲裁结算和链上审计。所有金额都是没有真实价值的 Sepolia 测试 ETH。

### 第一步：A 申请 Supplier，admin 批准

> 首先展示系统的角色准入。A 当前还没有 Supplier 权限，所以角色旁是红点。A 发起链上角色申请后，申请进入 Pending；admin 批准后，Supplier 变为绿点。后续创建发票的权限由 RoleRegistry 合约检查，仅仅在界面上选择一个角色并不能绕过权限。

### 第二步：A 创建发票

> A 现在以 Supplier 身份创建一张面值 0.05 ETH 的演示发票，并指定 B 为 Buyer。业务发票号由后端作为受权限控制的元数据保存，链上保存编号哈希、参与方、金额、日期和文档哈希。InvoiceRegistry 还会使用唯一键防止同一张发票在系统内被重复登记。

### 第三步：B 确认发票

> 现在切换到指定的 Buyer B。只有 B 能确认或拒绝这张发票。确认之后，发票进入 Confirmed，核心字段被锁定；没有 Buyer 的明确确认，Supplier 不能使用这张发票申请融资。

### 第四步：A 发起融资

> A 使用这张已确认、面值 0.05 ETH 的发票申请 0.04 ETH 融资，最高接受年化 8%，并设置 10% Holdback。每张发票同时只能有一个活跃融资申请，防止重复融资。

### 第五步：C 提交报价

> Funder C 对这笔融资提交年化 6% 的报价。合约会检查 C 的 Funder 权限、报价期限以及利率是否超过 Supplier 设置的 8% 上限。

### 第六步：A 接受报价

> A 选择并接受 C 的报价。此时只是锁定了融资条件，还没有发生放款；接下来只有被选中的 C 能在 24 小时窗口内提供资金。

### 第七步：C 放款

> C 向 FinancingPool 支付完整的 0.04 ETH 本金。合约立即向 A 支付 0.036 ETH，并将 0.004 ETH 作为 Holdback 留在池中。现在发票和融资都进入 Funded，资金拆分由合约规则执行。

### 第八步：B 在移动端发起 Dispute 并提交证据

> 接下来我们切换到手机宽度，展示同一套响应式 DApp 的移动端布局，包括单列卡片和底部导航。B 对已经放款的发票发起争议；前端会把原因文字计算成 Keccak-256 哈希，链上只保存哈希、提交人和时间，不公开原始材料。争议打开后，相关融资操作被冻结。B 再提交一条 Evidence hash，作为证据内容未被替换的链上凭证。

### 第九步：B 在争议期间还款

> 争议并不免除 Buyer 的付款义务。B 仍然支付完整的 0.05 ETH，但因为争议尚未解决，资金不会立即分给 Supplier、Funder 和平台，而是进入 FinancingPool 托管。发票状态变为 Repayment deposited，并且不能重复还款。

### 第十步：D 在移动端裁决

> 现在切换到同时拥有 Arbitrator 权限的 D，并继续保持移动端视图。D 能看到争议原因哈希、Evidence hash 和提交者，但看不到被哈希隐藏的原始文字或文件。Arbitrator 不能输入任意收款地址或金额，只能选择合约预定义的裁决。这里选择 Resume，合约解除冻结，并自动按照原有融资规则结算托管资金。最终发票进入 Repaid，融资进入 Settled。

### 第十一步：D 恢复桌面并展示 Audit

> 在展示审计前，我们恢复桌面视图。D 切换到只读的 Auditor 角色后，可以查看业务汇总、单张发票的完整资金流以及五个合约的事件时间线。Audit 数据是通过 RPC 实时读取的，数据库不保存链上业务镜像；交易哈希还可以跳转 Etherscan 独立核对。Auditor 页面没有修改业务状态的按钮。

### 结束总结

> 到这里，一张发票已经完成角色授权、Buyer 确认、融资、报价、放款、争议还款托管、预定义裁决、自动分账和审计闭环。智能合约始终是业务状态和资金结果的唯一事实来源。
